# StatePipes conventions

StatePipes implements the **state-scoped command handler** pattern: each state is a class, and it declares the
triggers it handles as annotated methods. The framework routes each trigger to the current state. There is no
routing code to write. Keep each state's behavior inside that state's class.

The reference is `docs/StateMachineComposition.md` in the StatePipes repository, and the rationale is
`docs/Paper.md`. A service repository doesn't contain them, so read them from the release URL given in
`statepipes-scaffold` → "Where the templates and documents are", using the service's StatePipes version. This
skill gives the rules and links to those documents rather than repeating them.

## Layout

A service generated by `new-service` (see `statepipes-scaffold`) has three projects:

```
<Prefix>/                         class library: all behavior lives here
  Builders/                       DefaultSetup.cs (container), DefaultServiceConfiguration.cs (proxies)
  Events/                         public events this service publishes
  ValueObjects/                   ProxyMonikers.cs and shared value types
  Proxies/                        generated proxies to other services (never hand-edited)
  StateMachines/<Machine>/
    <Machine>.cs                  IStateMachine marker
    States/                       one class per state
    Triggers/                     public triggers
    Triggers/Internal/            internal triggers
<Prefix>.Service/                 host: Program.cs, appsettings, Dockerfile. No behavior.
<Prefix>.Test/                    StateMachineForTest tests
```

Put new files where the matching scaffold operation would put them. Don't add behavior to `<Prefix>.Service`.

## Naming

- PascalCase for machines, states, triggers and events. The machine marker is `<Name>StateMachine`, for example
  the default `<Component>StateMachine`.
- Name states after the condition, for example `Idle`, `Running`, `Faulted`. Name triggers after the request or
  signal, for example `Start`, `Stop`, `ResetFault`, `PollTrigger`.
- Name events after facts that already happened, for example `PumpStartedEvent` or `CurrentStatusEvent`.
- Guard methods are `<Trigger>Guard`, as the scaffold templates name them. Periodic handlers are
  `<Name>PeriodicWorker`.

## Triggers

- **Public** triggers are in `Triggers/` and are `public class`. Other services can send them through a generated
  proxy, so they are part of the service's API. Change them deliberately.
- **Internal** triggers are in `Triggers/Internal/` and are `internal class`. Use them for signals that come from
  this service itself: timers, proxy connection status, and cross-machine firing.
- A trigger carries its payload as immutable properties. Every trigger inherits `BaseTriggerCommand<<Machine>>`,
  which ties it to exactly one machine.
- Reference: `docs/StateMachineComposition.md` sections 4 and 13.

## States and lifecycle

- Every side effect of entering or leaving a state belongs in `OnEntry` or `OnExit`: starting or stopping timers,
  publishing entered or left events, opening or closing resources. `OnActivate` and `OnDeActivate` run when the
  underlying machine activates or deactivates.
- The first state of a machine implements `IFirstStateForStateMachine`. The first child of a parent implements
  `IFirstSubstate` and is entered automatically with its parent.
- Use a parent state when several states share handling for the same trigger, for example a `Stop` handled in
  every running sub-mode. Define the handler once on the parent rather than in each child.
- Add a state by adding a class plus a handler in each state that leads to it. Don't change the existing
  transitions of other states. That additive property is what `docs/Paper.md` section 4 relies on.
- Reference: `docs/StateMachineComposition.md` sections 5 and 8.

## Guards

| Attribute | Returns `true` | Returns `false` |
|---|---|---|
| `[PermitIf(typeof(Dest))]` | Transition to `Dest` (`OnExit`, then `Dest.OnEntry`) | No transition from this state; see below |
| `[PermitReentryIf]` | Re-enter this state (`OnExit`, then `OnEntry`) | **The method body has already run**, and there is no re-entry. Use this to handle a command in place; see below |
| `[IgnoreIf]` | Trigger dropped on purpose | No ignore; see below |

**When every guard for the trigger in this state returns `false`**, the trigger goes to the parent state's handlers
for the same trigger, if the state has a parent (Stateless superstate lookup). If no ancestor handles it, it is
unhandled: it is dropped and logged at verbose level. So a child's side-effect-only `[PermitReentryIf]` that returns
`false` for `Stop`, under a parent with `[PermitIf(typeof(Idle))]` for `Stop`, runs its body **and then** the
parent's transition. To keep a trigger in the child, return `true` from a handler in the child, or don't handle that
trigger in the parent.

- Generated stubs return `true`. Replace each stub with the condition from the approved model.
- Guards run when the trigger arrives. Keep them fast and free of blocking calls.
- A trigger with no handler in a state is dropped. Leaving a handler out is a valid choice, so add one only where
  the model says the state reacts.
- Override `Configure` only for wiring that has no attribute, and call `base.Configure(stateConfig)` first.
- Reference: `docs/StateMachineComposition.md` sections 6, 7 and 14.

## Events and commands

- `PublishEvent(new SomeEvent(...))` broadcasts an `IEvent`. Events must be immutable, so use `record` types or
  `init`-only properties.
- `SendResponse(ev, responseInfo)` replies to the sender of the current trigger. `GetCurrentResponseInfo()`
  returns the sender.
- `SendCommand` sends a point-to-point command through the CommandBus.
- `FireExternal<OtherMachine, Trigger>(...)` fires a trigger into another machine of the same service.
- `SendCurrentStatusAllStateMachines()` pushes an `AllStateStatusEvent`. The generated `SendCurrentStatusCommand`
  and `CurrentStatusEvent` follow this pattern.
- `CreateDelayedMessageSender<T>()` returns a timer for timeouts and periodic work. `add-periodic` wires one into a
  state.
- Proxy topology is configured in `DefaultServiceConfiguration` (`ProxyConfigurations`), never by hand elsewhere.
- Reference: `docs/StateMachineComposition.md` sections 10 and 11.

## Framework rules

1. Never block on async work: no `.Result` and no `.Wait()` in state machine code or async loops.
2. Use `async`/`await`. Wrap long-running or fire-and-forget work with `TaskWrapper`.
3. Never delete or edit a `// Injection Point N, Do Not Delete or Modify` line or the `//@#$...@#$` using
   prefixes. The scaffold operations depend on them.
4. Don't hand-edit files under `Proxies/`. Regenerate them with `update-proxy`.
5. Run `dotnet format` before calling any change done. `statepipes-verify` checks this.
